> Part of the design system in swedol-ui-prototype. See `CLAUDE.md` for tech stack, breakpoints, and the quality checklist. This skill is the **process** for adding component skills; the reference example is `eco-radio` (form control) — compare against `eco-checkbox`/`eco-input` for siblings.

# Adding a component to the design system

Per `CLAUDE.md`: never create a new skill without asking. If the user has already asked for the component, that counts as the go-ahead for that component only.

## 1. Gather inputs (ask if missing)
- Figma link(s) with `node-id`: the **component set** (all variants) and, if it exists, the **usage/info frame**. Ask for **one frame per breakpoint** if the component differs by breakpoint (see memory: design-review ask-per-breakpoint).
- Sibling components it must stay consistent with (e.g. radio ↔ checkbox).

## 2. Extract from Figma (never from memory or guesswork)
1. Load `figma:figma-design-to-code`, then call `get_design_context` (pass `skillNames: figma-design-to-code`) for the component set and the info frame.
2. Call `get_variable_defs` on the same nodes → the exact token names + values Figma binds.
3. If the output is truncated or lacks geometry, download the exported SVG assets (`curl`) and read radii/strokes/sizes from them; use `get_screenshot` at high `maxDimension` for visual comparison.
4. Record: variant axes (Size, State, Breakpoint, Mode), dimensions, spacing, typography style names, per-state fill/border/text/icon tokens, focus ring spec, motion if any, and the **usage guidance text** from the info frame.

## 3. Map every value to a token
- Look up each Figma variable in `.claude/skills/eco-tokens/tokens.json` (`color.*`, `spacing.*`, `typography.*`, `border.*`, `shadow.*`) and write `var(--…)` names. Figma `color/border-hover` → `--color-border-hover`; `spacing/space-4` → `--dimension-spacing-space-4`.
- Value with no token → check `CLAUDE.md`, `eco-colors`, `eco-spacing`, `eco-typography`; else use the literal with a **visible comment** and list it under "flags" (CLAUDE.md quality rule 6/7). Never invent.
- Figma vs repo conflict (e.g. font size, colour hex, focus colour differs from the sibling component) → **do not silently pick**. Follow `tokens.json`, add a `> Flag for design` note in the skill, and mention it in your reply.
- Never edit `tokens.json` by hand (generated by `generate-tokens.py`); if a token is missing there, say so in a flag.

## 4. Write `.claude/skills/eco-<name>/SKILL.md`
Frontmatter: `name: eco-<name>`, `description: Use when …` (one line: when to use + what it covers, plus what it is NOT for). Then this fixed skeleton (omit a section only if truly N/A):

1. Header blockquote pointing to `CLAUDE.md`.
2. `## <Component> (ECO Design System)` + Figma node ids.
3. **When to use / not to use** — from the Figma info frame; name the sibling component to use instead.
4. **Size model** — table of dimensions per size (total area, visible element, margin, focus ring); state whether sizes change per breakpoint.
5. **Typography** — table linking to `eco-typography` styles; mobile-first, switching at `md` (769px), never `sm`.
6. **States** — one table, every variant state × (fill, border, text, icon, extras). Every Figma state must appear.
7. **HTML structure** — semantic, native elements first (`<input>`, `<button>`, `<fieldset>`), a11y attributes, real example incl. disabled/selected.
8. **CSS template** — hand-written CSS with `var(--…)` only, mobile-first `@media (min-width: 769px)`. **No Tailwind classes** (repo has no Tailwind build — see `eco-tokens`). Reuse existing classes/patterns from sibling skills before adding new ones.
9. **Dark mode / variants** — only if Figma has them.
10. **Rules** — numbered, numbered "Never"/"Always" items incl. the token rule, a11y rule (focus-visible, label association), and the breakpoint test line.
11. **Flags** — deviations/ambiguities found (Figma vs tokens, missing tokens).

Keep it thin: spec + template, no page-specific hacks.

## 5. Register it
- Add the component's documentation page in `eco-design-system/components/<name>.html` following `eco-doc-page` (replace its `Coming` card in `overview.html`, add a card in the root `index.html`).
- Add a row to the matching table in **`CLAUDE.md` → "Component library — skills index"** (Form components / Layout / Notifications / Links / Other), copying the skill's `description` as the "Used when" cell. New category → ask first.
- If a guide skill exists for the family (`links-guide`, `notifications-guide`) add the new type there.
- Update cross-references (e.g. `eco-segment-control` says "never replaces Radio buttons" → link to `eco-radio`).
- If the user mentions page renames/new pages, follow the index.html memory rules.
- Run `graphify update .` afterwards (CLAUDE.md graphify rule).

## 6. Verify before reporting done
1. **Render it**: create a scratch HTML (in the scratchpad, from `template.html` head so tokens load), paste the CSS template and every state (force hover/focus with classes or DevTools), compare against the Figma screenshot.
2. **Breakpoint check** with `getComputedStyle` at ~375px, ~700px, ~1024px+: size, font, colours match the skill's tables (CLAUDE.md quality rule 1). `sm` must look like mobile.
3. **Interaction** at mobile and desktop width: click label, keyboard (Tab/arrows/Space), disabled not focusable.
4. **Token audit**: grep the skill's CSS for `#[0-9a-fA-F]{3,8}` and bare `px` colours/spacing — every hit needs a comment or a `var()`.
5. **Consistency audit**: same structure/naming as sibling skills (`form-<name>-item` class pattern, same focus ring rule, same state table columns).
6. Report: what was added, the flags for design, anything unverified. State plainly what was *not* tested.

## Don'ts
- Don't copy a finished page as the source of CSS; derive from Figma + tokens.
- Don't add design-taste/other-skill styling (see CLAUDE.md "Precedence").
- Don't bundle unrelated component changes into the same edit.
