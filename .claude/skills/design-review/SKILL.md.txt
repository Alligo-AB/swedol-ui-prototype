# Design review: implementation vs. Figma + ECO (Fully Automated)

**Goal:** Clear, verified feedback that developers can act on immediately in Jira. Every item says what deviates, what it should be (Figma node or ECO token/skill), what the code does now, and a concrete fix. **Findings + images post automatically to Jira.**

## ⚡ Setup (One-time)

### 1. Install Atlassian MCP

The workflow requires the **Atlassian MCP** connector to read Jira tickets and post/update review comments. Generated comparison images are uploaded separately through the Jira REST attachment API.

1. Go to claude.ai → Connectors
2. Search for "Atlassian MCP" and install it
3. Authenticate with your Jira account (OAuth, no credentials stored)
4. Verify it's enabled in this chat (Connector settings)

### 2. Store Jira credentials (secure)

Create a `.env` file in the project root:

```bash
# .env (add to .gitignore)
JIRA_INSTANCE=alligo.atlassian.net
JIRA_CLOUD_ID=87d085b2-4edd-4bb5-9755-63e9292d0a69
JIRA_EMAIL=your_atlassian_account_email
JIRA_API_TOKEN=your_personal_access_token_here
```

**To get your Jira API token:**
- Go to https://id.atlassian.com/manage-profile/security/api-tokens
- Create a new token (name it "Claude Design Review")
- Copy the token and paste into `.env`
- Never commit `.env` to git

### 3. Verify Figma MCP (read-only)

Check that Figma MCP tools are available:
```
ToolSearch: figma
```
If Figma MCP is unavailable, stop the automated review and report that Figma MCP must be connected before the review can continue. Do not ask the user to manually provide screenshots as part of the normal automated workflow.

## Workflow: How It Works

When you run the design-review skill:

1. **Ask for Jira key** (e.g., "AE-3036")
2. **Read the ticket** → Extract and classify Figma frame links, UAT/staging implementation URL, prototype/reference URLs, and acceptance criteria. Never substitute a prototype/reference URL for UAT.
3. **Test implementation** → Compare the live UAT implementation against the linked Figma scope, Jira acceptance criteria, and ECO rules at the required responsive widths
4. **Generate findings** → Severity-categorized report (Critical, Should-fix, Nice-to-have, To-confirm, Figma issues)
5. **Create comparison images** → Figma vs. UAT side-by-side with marked deviations
6. **Post to Jira** → Comment + all images uploaded and embedded, all automatically
7. **Done** → Developers see full report + visual proof in one Jira comment

No manual image dragging. No copy-paste. Designer just says the Jira key and walks away.

## 1. Start from Jira — ask only if required information is missing

The Jira ticket is the starting point for every design review. The user should normally only need to provide the Jira key.

Read the Jira ticket first using Atlassian MCP and extract:

- acceptance criteria and relevant ticket description
- Figma node URL(s)
- UAT/staging implementation URL
- prototype/reference/demo URLs, if present
- any ticket-specific review instructions or relevant context

Do not ask the user for information that is already available in the Jira ticket.

Before continuing, verify that the required review inputs can be identified:

- at least one usable Figma source
- the UAT/staging implementation under review
- the Jira acceptance criteria and relevant ticket context

Classify all URLs according to their purpose before using them. A prototype, demo, Storybook page, or reference implementation must not be substituted for the UAT/staging implementation.

Check that Figma MCP is available for the linked Figma source and that UAT can be accessed using Claude in Chrome.

Use English and Markdown for the Jira review by default. Do not ask for report language or format unless the ticket or user explicitly requires something different.

Ask the user for input only when an essential dependency cannot be resolved automatically. Examples include:

- the Jira ticket contains no usable Figma source
- the Jira ticket contains no identifiable UAT/staging URL
- multiple URLs could plausibly be the implementation under review and the ticket does not disambiguate them
- the linked Figma node cannot be accessed
- UAT requires the user to authenticate manually in Chrome
- the intended Figma-to-UAT component mapping remains genuinely ambiguous after using the Jira ticket context

When blocked, ask only for the specific missing or ambiguous information required to continue.

Do not ask the user to manually provide information that can be retrieved from Jira, Figma MCP, Claude in Chrome, or the configured project tooling.

The normal successful workflow should require no further interaction after the user provides the Jira key.

## Implementation target — Figma vs UAT

The three sources have different roles:

- **Figma = design source of truth.** This defines the expected visual design.
- **UAT/staging = implementation under review.** This is the only implementation that may be used for "Currently" measurements and implementation findings.
- **Prototype/reference URLs = reference only.** Vercel prototypes, local prototypes, Storybook examples, demos, or other reference implementations may be inspected for supplementary context, but they are not the implementation under review.

The primary review comparison is always:

**Figma (expected) → UAT/staging (currently implemented)**

### Figma review scope

The Figma node linked from the Jira ticket defines the design scope of the review.

If the Jira Figma URL points to a specific component, variant, frame, section, or element:

- Treat that linked node as the Figma source of truth for the visual review.
- Find the corresponding implementation on UAT and compare it against that linked Figma node.
- Do not expand the visual review to sibling components, other form controls, other Figma frames, or the entire Figma page unless the Jira ticket explicitly requires it.
- The UAT URL may point to a full page. Locate the implementation corresponding to the linked Figma node within that page.
- Use surrounding Figma content only when necessary to understand context, positioning, responsive behaviour, or relationships required by the acceptance criteria.
- Do not report unrelated visual differences outside the linked Figma scope.
- If multiple Figma node URLs are provided in Jira, each linked node is part of the visual review scope.

The Jira acceptance criteria remain part of the review. If an acceptance criterion explicitly requires validation outside the linked Figma node, validate that criterion, but do not automatically broaden the visual Figma comparison beyond the linked node(s).

When reading the Jira ticket, classify URLs by their stated purpose. Do not assume that a URL labelled prototype, reference, demo, example, or similar is the UAT/test implementation merely because it is a runnable webpage.

If Jira contains both a prototype/reference URL and a UAT/staging URL:

- Use the UAT/staging URL for all implementation measurements and findings.
- Use the prototype only as supplementary context.
- Comparison images must compare Figma with UAT/staging, not Figma with the prototype.
- Every value reported as "Currently" must have been measured from the live UAT/staging implementation.

If Jira contains a Figma URL and prototype/reference URL but **no identifiable UAT/staging implementation URL**, stop before performing the implementation review. Report that the UAT/staging URL is missing. Do not substitute the prototype/reference URL.

Before beginning measurements, explicitly identify internally:

- Figma source of truth and linked node(s)
- Figma visual review scope
- UAT/staging implementation under review
- Any prototype/reference URLs

Only continue once the implementation-under-review URL has been identified.

### Matching Figma scope to UAT

After determining the Figma review scope, identify the corresponding implementation on UAT before measuring, capturing, or reviewing it.

Use all available ticket context to identify the intended UAT element, including:

- Jira acceptance criteria
- component or feature names
- labels and surrounding content
- component purpose
- linked Figma context
- page context on UAT

Do not select an element merely because it visually resembles the linked Figma component or uses the same generic component type.

For example, if the Jira acceptance criteria refer to a **Search input**, do not substitute an Email, Password, or other Input field simply because the linked Figma node represents the generic Input component.

Before measuring the implementation, establish and record the mapping:

**Figma scope → Jira requirement → UAT element**

Example:

**Base / Input → Search input → `<input type="search" ...>`**

If multiple UAT elements could plausibly correspond to the Figma scope, use the Jira acceptance criteria and page context to disambiguate them.

If the corresponding UAT element still cannot be identified with reasonable confidence, stop and report the ambiguity. Do not choose another visually similar component instance as a substitute.

## 2. Read the design

- Load `figma-design-to-code` before `get_design_context`. Large frames come back as sparse metadata — call `get_design_context` on the sub-layers (page title, toolbar, table, pagination, mobile card) instead.
- Note which values are bound to variables/text styles and which are hardcoded **in Figma itself**. Figma's own local deviations go in a separate "Issues in the Figma file" section.
- Also search the ECO library when a component's origin is unclear.

## 3. Measure the implementation

- **UAT must be inspected as a live rendered page.** Open the exact UAT URL from the Jira ticket using Claude in Chrome. Do not base the implementation review only on screenshots, source code, or assumptions. The live rendered UAT implementation is the source for all "Currently" measurements.
- **Protected UAT.** UAT may be protected by an initial authentication/login or security gateway. Always access UAT using **Claude in Chrome** so the review uses the user's existing Chrome browser session, cookies, and authenticated state. Do not switch to another browser, HTTP fetch, headless browser, or unauthenticated session to bypass the login. Never ask for, store, or type the user's credentials. If the UAT security/login screen blocks access, ask the user to authenticate manually in that Chrome session. After the user has authenticated, continue the review using the same Chrome session and exact UAT URL.
- **Measure the implementation — do not estimate from screenshots.** For every reported spacing, size, typography, colour, border, radius or layout deviation, inspect the live UAT element and use browser/computed-style information where available. Record the actual measured UAT value and compare it with the corresponding Figma value and ECO token/rule.
  Example:
  - Finding: S1 — Card padding
  - Figma: 24px
  - ECO: `spacing-24`
  - UAT measured: 66px
  - Difference: +42px
  - Evidence image: mark the affected padding area and label it `S1`
- **Widths.** Check at least 375, 639, 640, 700, 768, 769, 1024 and the desktop frame width. Confirm the mobile→desktop switch happens exactly between 768 and 769.
- **Tokens.** Check `:root` for ECO variables and scan stylesheet rules to see whether values use tokens, legacy variables or literals.
- **States and accessibility.** Hover, keyboard focus, sortable headers (`<button>`, `aria-sort`), visible `<h1>`, tooltips.
- **Acceptance criteria.** Test the behaviour the ticket asks for (search, sorting, rows per load).

## 4. Verify before you report

Every claim of a *visible* difference must be checked by rendering or measuring it. If unsure whether something is intentional, put it under "To confirm" and ask.

## 5. Severity

| Level | Meaning |
|---|---|
| 🔴 **Critical** | Breaks the design system / tokens, breaks WCAG, or is visibly wrong. |
| 🟠 **Should fix** | Smaller but noticeable deviation. |
| 🟢 **Nice-to-have** | Polish, marginal. |
| ❓ **To confirm** | Possibly intentional, platform-level, or a design decision — needs an answer. |

## 7. Comparison images (automatic)

The workflow generates annotated comparison images automatically:

- **Figma side:** Downloaded via Figma MCP.
- **Implementation side:** Captured from the live UAT implementation using Claude in Chrome.
- **Composed:** Figma + UAT side-by-side.
- **Annotated:** Confirmed deviations are marked directly on the image.
- **Tagged:** Use the same finding IDs as the written review where applicable (C1, S-2, etc.).
- **Uploaded:** Automatically to Jira via the Jira REST attachment API.

### UAT comparison crop

When the linked Figma scope is a specific component or element, capture or crop the corresponding UAT component at a useful scale rather than showing the entire page.

Include enough surrounding context to identify the component, but prioritize making the compared Figma and UAT elements large enough for visual differences and annotations to be clearly visible.

Unrelated page content should not dominate the comparison image.

The UAT element used in the image must be the implementation corresponding to the linked Figma scope. Do not substitute another visually similar instance of the same component type.

### Comparison image annotations

A comparison image is not complete merely because Figma and UAT screenshots have been placed side-by-side.

The image must visually communicate the specific confirmed findings discovered during the review.

For every confirmed visual discrepancy shown in the comparison image:

- Add a numbered finding marker, outline, arrow, measurement line, or other clear visual indicator directly on or beside the affected UAT area.
- Add a concise annotation describing the discrepancy.
- Use the same finding ID as the written Jira review where applicable.
- Where the property is measurable, show both values:
  - **Figma:** expected value
  - **UAT:** currently measured value
- Prefer concrete measurements such as spacing, dimensions, font size, line height, border width, radius, or color/token value rather than vague descriptions.
- When the expected value maps to an ECO design token, include the token when useful.
- Make it visually clear which part of the UAT implementation each annotation refers to.

Example annotation:

**S1 — Input height**  
Figma: 58px  
UAT: 48px  
Expected: 58px

Do not add generic captions such as "compare padding, typography and colors" without identifying an actual confirmed difference.

Do not annotate a property unless it has actually been inspected or measured. Never invent measurements from visual estimation when an exact value can be obtained from Figma metadata or the live UAT DOM/computed styles.

If no confirmed visual discrepancies exist, explicitly label the comparison as having no confirmed visual differences rather than inventing annotations.

The purpose of the comparison image is that a developer should be able to understand the visual problem and expected correction without needing to read the entire Jira comment.

### Comparison image generation

Use the reusable comparison-image generator included with this skill:

`.claude/skills/design-review/scripts/generate-comparison.py`

Do not write ad-hoc Python or Pillow image-composition code during a design review.

### Generator dependencies

The comparison-image generator uses Pillow.

Do not automatically install, upgrade, or modify Python packages during a design review.

Before using the generator, verify that Pillow is available:

`python3 -c "from PIL import Image; print('Pillow available')"`

If Pillow is available, continue without installing anything.

If Pillow is unavailable, stop and report the missing dependency. Do not run `pip install`, `pip3 install`, or otherwise modify the user's Python environment automatically.

Before generating the comparison image:

1. Complete the Figma and UAT measurements.
2. Build an evidence matrix containing the exact values retrieved from each source.
3. Determine the confirmed differences from that evidence.
4. Exclude unverified, estimated, or matching properties from the visual findings.
5. Identify the corresponding UAT component and the crop coordinates needed to show it clearly.

Then call the reusable comparison-image generator with the confirmed finding data and source screenshots.

Temporary screenshots and generated comparison images must be stored under `/tmp`, not in the project repository.

### Comparison image filenames

Use the following naming convention for generated comparison images:

`/tmp/<JIRA-KEY>_comparison_<FINDING-ID>.png`

Examples:

- `/tmp/AE-3512_comparison_S1.png`
- `/tmp/AE-3036_comparison_C1.png`
- `/tmp/AE-3036_comparison_S2.png`

The Jira key and finding ID must correspond to the current review and written finding.

Do not use generic filenames such as `comparison.png`, `review.png`, or `screenshot.png`.

If one comparison image contains multiple findings, include all finding IDs in the filename, separated by underscores:

`/tmp/AE-3036_comparison_C1_S1_S2.png`

Temporary source screenshots used to construct comparison images may use implementation-specific temporary names, but the final Jira comparison image must follow this convention.

If the generator fails, report the failure rather than replacing it with newly generated image-composition code.

No manual screenshot needed. No manual image insertion needed.

## 8. Automatic Jira posting (No manual steps)

### Setup

Before running the skill, ensure:

1. ✅ Atlassian MCP is installed and enabled in this chat
2. ✅ `.env` file exists with `JIRA_INSTANCE`, `JIRA_CLOUD_ID`, `JIRA_EMAIL`, and `JIRA_API_TOKEN`
3. ✅ `.env` is in `.gitignore` (never commit tokens)

### The skill will:

1. **Post the markdown report** as a Jira comment using Atlassian MCP's `addOrEditJiraIssueComment`
2. **Upload comparison images directly via the Jira REST API — never through the Jira browser UI.**
   - Do NOT click Jira's attachment, image, upload, or "select image" controls.
   - Do NOT open a browser file-picker dialog.
   - Do NOT use browser automation to upload generated images.
   - Upload each generated PNG directly from its local filesystem path using `curl` and the Jira REST API.
   - Load the Jira credentials from the project's `.env` file.
   - This upload is non-interactive and must not require any user action.

```bash
# Use the exact final output path that was passed to the comparison-image generator.
COMPARISON_IMAGE="/tmp/AE-3036_comparison_C1_S1_S2.png"
# COMPARISON_IMAGE must be the exact --output path used by the comparison-image generator.
# Do not reconstruct or guess the filename during upload.

# Upload each image exactly once and capture the attachment response.
UPLOAD_RESPONSE=$(curl -sS -X POST \
  "https://api.atlassian.com/ex/jira/${JIRA_CLOUD_ID}/rest/api/3/issue/${JIRA_KEY}/attachments" \
  --user "${JIRA_EMAIL}:${JIRA_API_TOKEN}" \
  -H "X-Atlassian-Token: no-check" \
  -F "file=@${COMPARISON_IMAGE}")

# Read the attachment ID and filename from that same response.
echo "$UPLOAD_RESPONSE" | jq '.[0] | {id, filename}'
```
**Important:** Upload each generated image exactly once.

The successful POST response already contains the Jira attachment ID and filename. Capture and reuse that response.

Do not make a second POST request to retrieve the attachment ID. A second POST uploads the same image again and creates a duplicate Jira attachment.

3. **Attach comparison images to the Jira ticket.** Inline embedding in the comment is optional. Reference each uploaded image by filename and caption in the review comment.

### Result

Developers see in the Jira ticket comment:
- Full report text (Critical → Nice-to-have → To-confirm → Figma issues)
- Comparison image(s) with captions, generated as needed for confirmed findings
- All in one comment, ready to act on

**No designer action needed after triggering the skill.**

## 9. Error handling

**If Atlassian MCP is not connected:**
- Fall back to generating a `.md` file the user can manually paste
- Save the report and generated images under `/tmp`; do not create temporary review artifacts in the project repository.
- Warn: "Automatic posting is not configured. Please enable Atlassian MCP in connector settings."

**If Jira credentials are missing:**
- Look for `.env` file
- Verify `JIRA_INSTANCE`, `JIRA_CLOUD_ID`, `JIRA_EMAIL`, and `JIRA_API_TOKEN` are present
- If any are missing, ask the user to add them using the setup instructions above
- Do NOT prompt for the email or token in chat

**If image upload fails:**
- Do NOT fall back to Jira's browser upload UI or a file-picker dialog.
- Verify that the project's `.env` has been loaded and that `JIRA_CLOUD_ID`, `JIRA_EMAIL`, and `JIRA_API_TOKEN` are available.
- Retry the Jira REST API upload using the generated image's actual local filesystem path.
- Capture and inspect the HTTP response.
- If the REST API still fails, post the text report to Jira and tell the user the exact HTTP status/error returned by the attachment API.
- Never ask the user to manually upload the generated images as part of the normal workflow.

## 10. Corrections

If a finding turns out wrong:
1. Edit the report file
2. Re-run the Jira upload (update the existing comment or post a new one)
3. Tell the user what changed

## Troubleshooting

| Issue | Solution |
|---|---|
| "Atlassian MCP not available" | Install from claude.ai → Connectors |
| "JIRA_API_TOKEN not found" | Create `.env` file in project root with token |
| "401 Unauthorized" | Check that token is valid at https://id.atlassian.com/manage-profile/security/api-tokens |
| "Cannot read Figma frames" | Verify Figma MCP is connected and run `ToolSearch: figma`. If Figma MCP is unavailable or the linked node cannot be accessed, stop and report the blocker. |
| "Image upload returns 403" | Jira token may lack attachment permissions; regenerate token with full scope |
